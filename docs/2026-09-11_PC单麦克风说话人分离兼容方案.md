# PC 单麦克风说话人分离兼容方案

> 日期：2026-09-11
> 状态：P0 实施中（功能开关默认关闭，尚未部署）
> 原则：PC 浏览器录音作为默认入口，H5 作为可选增强；只增加说话人分离能力，不改变现有会议流程。

## 1. 要解决的问题

当前 PC 浏览器可以录音、实时转写、分片上传和生成会后纪要，但同一会议室多人共用一个麦克风时，实时记录通常会归到当前登录人，无法区分不同发言者。

目标体验：

1. 管理层打开 PC 浏览器即可开会，无需所有人通过 H5 加入。
2. PC 完整录音在会后自动区分为“发言人 1、发言人 2……”并关联转写。
3. 已注册声纹且匹配可信时，匿名发言人自动替换为真实姓名。
4. H5 仍然可以加入，并继续提供准确的登录身份和独立录音来源。
5. 分离服务失败或 GPU 繁忙时，现有录音、转写、纪要、结束会议和归档流程仍可正常工作。

## 2. 概念与展示规则

### 2.1 说话人分离

从一条混合录音中判断“这里换了一个人说话”，输出匿名标签：

- 发言人 1
- 发言人 2
- 发言人 3

它能区分不同声音，但不能直接证明真实身份。

### 2.2 声纹匹配

将匿名发言人的声音特征与已注册声纹比对。只有超过可信阈值才显示真实姓名：

- `李某 · 声纹匹配 86%`
- `发言人 2 · 未匹配身份`

界面不把匿名分离结果称为“已识别某人”，避免误导。

### 2.3 H5 身份

H5 录音与登录参会人绑定，显示：

- `丁志强 · H5 本人录音`

H5 身份证据优先于 PC 自动推断结果。

## 3. 推荐产品形态

### 3.1 默认开会方式

PC 页面主操作保持“电脑录音”。主持人点击一次即可开始：

1. PC 实时采集会议室声音。
2. 当前实时转写继续出现，不等待声纹模型。
3. 音频继续按现有机制分片上传。
4. 结束会议后先保证完整录音落盘，再异步进行 Whisper 终审和说话人分离。

H5 入口保留为“手机加入”，适用于远程参会、会议室收音不足、需要本人身份确认或需要独立音轨的场景。

### 3.2 会中页面

PC 实时阶段不承诺准确身份。未完成分离前统一显示：

- `会议室麦克风 · 实时转写`

如果实时声纹匹配已经可靠，可以显示姓名，但必须带来源和置信度；低置信度继续显示会议室麦克风。

### 3.3 会后页面

Whisper 终审转写区域增加身份来源：

- `发言人 1 · PC 自动分离`
- `李某 · 声纹匹配 86%`
- `丁志强 · H5 本人录音`
- `系统管理员 · 人工确认`

支持把某个匿名发言人批量重命名。人工确认后，同一分离标签的相关发言统一更新，并记录修改日志。

## 4. 数据优先级

同一段发言的身份按以下顺序决定：

1. 人工确认
2. H5 登录身份
3. 高置信度声纹匹配
4. PC 匿名说话人分离
5. 会议室麦克风

低优先级结果不得覆盖高优先级结果。

建议统一使用以下来源值：

| 来源 | 展示 | 是否可自动覆盖 |
| --- | --- | --- |
| `manual` | 人工确认 | 否 |
| `h5-authenticated` | H5 本人录音 | 仅人工可改 |
| `voiceprint-diarization` | 声纹匹配 | 可被人工/H5 覆盖 |
| `speaker-diarization` | PC 自动分离 | 可被声纹/H5/人工覆盖 |
| `room-microphone` | 会议室麦克风 | 可被其他来源覆盖 |

## 5. 后端处理方案

### 5.1 保持原链路

以下现有行为不修改：

- PC 麦克风授权和录音开关
- MediaRecorder 分片上传
- 上传失败重试
- 完整录音合并
- 未完成上传时禁止结束会议
- Whisper 终审
- H5 会话、录音和转写
- 纪要生成、审核和归档

### 5.2 增加异步分离任务

完整录音合并成功后新增独立任务：

```text
完整 PC 录音
  → 音频标准化（16kHz / mono）
  → pyannote 说话人分离
  → 生成带开始、结束时间的匿名说话人片段
  → 可选声纹匹配
  → 与 Whisper 时间戳对齐
  → 保存派生结果
  → SSE 通知 PC 刷新
```

任务状态建议：

- `idle`
- `queued`
- `running`
- `done`
- `failed`

分离任务不得成为结束会议和纪要生成的硬前置条件。

### 5.3 与 Whisper 对齐

Whisper 已输出分段时间戳。对每条 Whisper 片段：

1. 计算它与说话人片段的时间重叠。
2. 使用重叠时长最大的说话人标签。
3. 如果一条长句跨越多个说话人，按停顿和时间边界拆分。
4. 重叠不足或模型不确定时，保留“会议室麦克风”，不强行指派。

### 5.4 PC 与 H5 混合会议

不能简单把 PC 和 H5 音频顺序拼接后再分离，因为它们可能是同一时间的重复声音。

推荐规则：

1. PC 完整录音作为会议室主时间轴。
2. H5 转写保留自己的身份和时间戳。
3. 时间接近且文本高度相似时视为同一发言，优先采用 H5 身份。
4. PC 中未被 H5 覆盖的片段继续使用匿名分离或声纹匹配结果。
5. 不删除原始 PC/H5 证据，只在统一阅读视图中去重。

## 6. 数据保存方式

第一阶段不修改数据库 Schema。派生结果继续写入现有 JSON/事件结构，建议记录：

```json
{
  "speakerLabel": "SPEAKER_00",
  "speakerDisplayName": "发言人 1",
  "speakerUserId": "",
  "speakerConfidence": 0.82,
  "identifiedBy": "speaker-diarization",
  "audioSource": "desktop",
  "start": 12.4,
  "end": 18.9
}
```

匿名编号按每场会议第一次出现的顺序稳定映射，重新打开页面或重新整理记录时不能变化。

## 7. GPU 与任务调度

Whisper 和 pyannote 都可能占用 GPU1，不能无控制地同时运行。

建议：

1. 使用独立并发锁，GPU1 同时最多运行一个重任务。
2. Whisper 终审优先，完成后再执行说话人分离。
3. 页面显示“正在进行说话人分离”，不阻塞用户继续审核现有纪要。
4. GPU 不可用时记录失败原因，并提供“重新分离发言人”按钮。
5. 重试只重跑派生分析，不重新上传录音、不重复生成纪要。

## 8. 前端交互

### 8.1 录音入口

保留现有两个入口：

- `电脑录音`：默认推荐
- `手机加入`：可选增强

电脑录音说明调整为：

> 适合会议室多人共用一台电脑。会后将自动区分不同发言人；已登记声纹时可尝试匹配姓名。

### 8.2 状态反馈

会中：

- 电脑录音中
- 正在保存录音
- 录音已保存

会后：

- 等待说话人分离
- 正在区分发言人
- 已区分 4 位发言人
- 分离失败，可重新尝试

### 8.3 人工校对

点击“发言人 1”可以：

- 选择现有参会人
- 输入临时姓名
- 批量应用到同一声纹标签
- 仅修改当前一条

系统必须展示“自动分离”“声纹匹配”“H5 本人”“人工确认”等来源。

## 9. 失败回退

| 异常 | 系统行为 |
| --- | --- |
| pyannote 未安装或模型不可用 | 保留现有转写，显示会议室麦克风 |
| GPU1 忙 | 排队等待，不阻塞结束会议 |
| 分离任务失败 | 保存失败状态，允许手动重试 |
| 声纹匹配置信度不足 | 使用匿名发言人，不猜姓名 |
| PC 与 H5 内容重复 | 阅读层去重，原始证据都保留 |
| 人工已经确认身份 | 后续自动任务不得覆盖 |

## 10. 分阶段实施

### P0：PC 匿名说话人分离

- 接入完整 PC 录音的 pyannote 分离任务。
- 生成稳定的“发言人 1 / 2 / 3”。
- 对齐 Whisper 时间戳。
- 会后页面展示分离状态和身份来源。
- 失败自动回退现有逻辑。

### P1：真实声纹匹配与人工校对

- 匹配已注册声纹。
- 低置信度不显示真实姓名。
- 支持批量重命名匿名发言人。
- 记录人工修改日志。

### P2：PC 与 H5 混合去重

- 基于时间和文本相似度对齐重复内容。
- H5 登录身份优先。
- 统一阅读视图去重，保留全部原始证据。

## 11. 验收标准

### PC 单机多人会议

- 一台 PC 录制至少 3 位发言人。
- 会中实时转写不受影响。
- 结束会议和音频上传逻辑不变。
- 会后能够稳定显示至少 3 个匿名发言人标签。
- 刷新页面后匿名编号不变化。

### 声纹匹配

- 已注册声纹且置信度达标时显示真实姓名和置信度。
- 未达标时只显示匿名标签。
- 人工修改后不会被自动任务覆盖。

### PC + H5

- H5 转写继续实时同步到 PC。
- H5 身份不被 PC 匿名结果覆盖。
- 同一段声音不会在统一阅读视图重复出现两次。

### 回归

- PC 录音开始、暂停、上传和结束会议通过。
- H5 加入、录音、上传和结束会议通过。
- 无声纹服务时仍可生成纪要并归档。
- 重新整理记录不重跑 AI；重新生成纪要仍遵守当前幂等规则。

## 12. 本次改造边界

本方案不包含：

- 强制参会人注册声纹
- 用匿名分离结果自动认定真实身份
- 修改会议阶段和归档规则
- 修改数据库 Schema
- 更换现有 ASR 或 Whisper 模型
- 将说话人分离设为结束会议的前置条件

确认后建议先实施 P0，并使用一段包含 2–4 位发言人的真实会议室录音验收，再决定是否启用 P1 的自动姓名匹配。

## 13. PC 录音中的姓名识别策略

PC 单麦克风只能先判断“出现了不同的声音”，不能仅凭音频直接知道真实姓名。系统必须通过身份锚点将匿名说话人与参会人关联。

身份来源按以下优先级处理：

1. 人工确认：管理员将“发言人 1”指定为某位参会人。
2. H5 登录身份：参会人通过本人账号加入后提供身份明确的语音样本。
3. 已注册声纹：与系统已有声纹档案进行高置信度匹配。
4. 本场临时声纹：本场会议中已经确认过的声音继续复用姓名。
5. 匿名分离：没有可靠身份时显示“发言人 1 / 发言人 2”。

界面展示规则：

- `丁志强 · 人工确认`
- `李某 · H5 本人录音`
- `王某 · 声纹匹配 88%`
- `发言人 3 · 待确认`

系统可以从“大家好，我是……”等自我介绍中提取候选姓名，但只能显示“可能是某某，请确认”，不能自动认定身份。正文中提到别人的姓名不构成身份依据。

人工将匿名发言人绑定到姓名后：

- 默认批量应用到本场会议相同的稳定说话人标签。
- 已经人工确认的结果不允许被后续自动任务覆盖。
- 用户可以选择只用于本场会议，或者经确认后沉淀为长期声纹档案。
- 所有自动匹配和人工修改都保留来源、置信度、操作人和操作时间。

## 14. 现有录音链路保护要求

说话人分离必须作为完整录音落盘后的旁路任务接入，禁止嵌入或改写当前录音主链路。

当前主链路保持不变：

```text
麦克风授权
  → MediaRecorder 开始录音
  → 3 秒分片
  → 分片上传与重试
  → 服务端 ACK
  → 停止录音
  → 等待未完成上传
  → 服务端合并并校验完整性
  → 允许结束会议
  → Whisper 终审
```

说话人分离只能在“服务端合并并校验完整性”成功后读取完整音频副本：

```text
已校验的完整录音（只读）
  ├── 现有 Whisper 终审
  └── 新增说话人分离旁路任务
```

### 14.1 禁止修改的行为

- 不改变 MediaRecorder 参数、分片时长和分片顺序。
- 不改变上传接口、ACK、断点续传和失败重试语义。
- 不改变录音 manifest 和完整性校验规则。
- 不改变“存在未上传手机录音时禁止结束会议”的逻辑。
- 不改变 PC 停止录音时等待上传和合并完成的逻辑。
- 不把 pyannote、声纹匹配或姓名确认设为结束会议前置条件。
- 不因分离失败删除、重写或重新编码原始录音。
- 不修改当前 Whisper 终审结果的原始证据。
- 不修改 H5 已绑定的本人身份。
- 第一阶段不修改数据库 Schema。

### 14.2 技术隔离

- 新任务通过独立服务模块读取完整 WAV，不直接持有浏览器录音会话状态。
- 使用独立任务状态和错误字段，失败状态不得写入录音 manifest。
- 使用独立功能开关，默认关闭；关闭后系统行为必须与改造前一致。
- 同一会议、同一完整录音使用稳定任务键，重复点击不得创建两个分离任务。
- 重新分离只重跑派生结果，不重新上传、合并或终审原始录音。
- 派生结果单独保存，原始转写、录音事件和音频文件保持可追溯。
- GPU 调度与录音上传线程隔离，GPU 排队不得影响音频网络请求。

建议功能开关：

```text
SPEAKER_DIARIZATION_ENABLED=false
```

正式启用前先在测试会议开启，完成回归后再切换生产默认值。功能开关的实际配置变更属于部署步骤，不在方案阶段修改。

### 14.3 上线门槛

只有以下检查全部通过，才能部署到 44：

1. 不开启说话人分离时，PC 和 H5 录音行为与当前生产版本一致。
2. 开启说话人分离后，分片数量、ACK 数量、合并文件时长和大小没有异常变化。
3. 分离进程主动失败时，仍能结束会议、播放录音、查看转写并生成纪要。
4. GPU1 忙或模型未加载时，录音上传不超时、不丢片、不重复上传。
5. 重复触发分离只复用同一任务结果。
6. H5 未上传完成时仍然禁止结束会议。
7. PC 上传失败时仍然显示当前错误并允许重试。
8. 原始音频、原始转写、Whisper 终审和分离结果可以分别追溯。
9. 至少完成 PC 单机、H5 单机、PC 与 H5 混合三类真实录音回归。

### 14.4 发布与回退

- 第一版仅发布代码并保持功能开关关闭。
- 在指定测试会议中灰度开启，观察任务耗时、GPU1 显存、分离人数和失败率。
- 验收通过后再对新会议默认启用，不自动重跑历史会议。
- 出现异常时关闭功能开关即可回到现有录音和转写行为，无需回滚录音数据。
- 已产生的分离结果属于派生数据，关闭功能后不参与正式展示和纪要生成。

## 15. 说话人分离技术选型

### 15.1 选型结论

pyannote 技术路线仍适合本项目，但不再以旧的 `pyannote/speaker-diarization-3.1` 作为新功能默认模型。

P0 默认采用：

```text
pyannote.audio 4.x
+
pyannote/speaker-diarization-community-1
```

现有实时 ASR、Qwen3-ASR 二次校正、Whisper large-v3 终审和纪要模型均不替换。Community-1 只负责读取已经完整落盘的 PC 录音，生成说话人时间段和匿名标签。

### 15.2 选择 Community-1 的原因

- pyannote 仍在持续维护，不属于废弃技术。
- Community-1 是 3.1 之后的新一代开源说话人分离流水线。
- 相比 3.1，它改善了说话人数估计和说话人分配。
- 支持 `exclusive_speaker_diarization`，更适合与 Whisper 时间戳对齐。
- 可以输出每位说话人的 embedding，便于后续匹配现有声纹档案。
- 模型可以下载到 44 后完全离线运行。
- 当前项目已有 pyannote 封装，接入范围小于更换整套说话人分离框架。

官方公开基准中，Community-1 在中文会议数据上的说话人错误率优于 3.1：

| 数据集 | speaker-diarization-3.1 | Community-1 | 说明 |
| --- | ---: | ---: | --- |
| AISHELL-4 | 12.2% | 11.7% | 中文多方会议 |
| AliMeeting 单通道 | 24.5% | 20.3% | 更接近 PC 单麦克风会议室场景 |

错误率仍然不能支持系统直接认定真实姓名。因此 Community-1 只负责“谁在什么时候说话”；真实姓名继续遵守人工确认、H5 身份和高置信度声纹匹配规则。

### 15.3 不直接采用 Sortformer 的原因

NVIDIA NeMo Sortformer 是值得评估的现代端到端说话人分离方案，支持离线和流式处理。当前不将它作为 P0 默认引擎，原因如下：

- 本项目第一阶段只需要会后处理完整录音，不需要实时分离。
- 现有后端已经封装 pyannote，使用 Community-1 的改动范围更可控。
- 引入 NeMo 会增加独立运行环境、模型部署和显存评估工作。
- 部分官方 Sortformer 预训练模型限制最多四位说话人，不适合直接作为所有会议的唯一实现。
- 当前首要约束是不能影响已有 PC/H5 录音主链路。

Sortformer 保留为 P2 对照引擎，不在第一阶段进入生产主路径。

### 15.4 对照测试条件

完成 Community-1 P0 后，使用同一批真实中文会议室录音比较 Community-1 与 Sortformer：

- 2 人、4 人和 5 人以上会议。
- 近场、远场和环境噪声。
- 快速轮换发言和多人重叠发言。
- 已知真实发言人的人工标注样本。
- 相同硬件下的处理时长、显存峰值和失败率。
- 与 Whisper 时间戳对齐后的姓名归属准确率。

只有 Sortformer 在真实样本上取得明确收益，并且没有增加录音主链路风险时，才考虑增加为可选引擎或替换默认引擎。

### 15.5 44 部署约束

- Community-1 模型预先下载到服务器本地，生产处理不依赖外网。
- 模型文件和依赖放在独立运行环境，不修改现有 ASR 环境。
- 先检查 44 当前 pyannote 运行时为何返回未就绪，再决定升级方式。
- 不直接覆盖旧模型目录，保留回退能力。
- Whisper 与 Community-1 在 GPU1 串行运行，同一时间只运行一个重任务。
- 功能开关关闭时不加载 Community-1，不额外占用 GPU 显存。
- 模型加载失败只记录旁路任务错误，不能影响录音上传、会议结束和 Whisper 终审。

### 15.6 与现有 H5 链路的隔离关系

当前 `pyannote/speaker-diarization-3.1` 只在声纹引擎中声明，尚未被正式业务流程调用完整录音的 `diarize()`。它目前不属于 H5 录音、上传和实时转写主链路。

H5 当前链路保持如下：

```text
H5 登录身份
  → 手机麦克风录音
  → 实时 ASR WebSocket
  → 转写分片写入
  → 音频分片上传与服务端 ACK
  → 停止录音并等待上传完成
  → 服务端合并和完整性确认
```

H5 姓名来源首先是登录身份。当前可选的实时声纹增强使用 `identify_speaker_from_bytes()` 和声纹 embedding 进行比对，不调用 `speaker-diarization-3.1` 的完整录音分离流程。声纹增强不可用时，现有代码会跳过增强并继续 ASR。

Community-1 接入后的边界必须保持为：

```text
H5 实时录音、转写和身份链路
  → 保持现状，不调用 Community-1

PC 已完整落盘的会议室录音
  → Community-1 会后旁路分析
```

禁止事项：

- 不使用 Community-1 替换 H5 实时 ASR。
- 不让 Community-1 参与 H5 分片上传、ACK 或断点续传。
- 不使用 PC 匿名分离标签覆盖 H5 登录姓名。
- 不修改 H5 的 `participantId`、`audioClientId` 和设备归属关系。
- 不修改“存在未上传完成的 H5 录音时禁止结束会议”的规则。
- 不因 Community-1 排队、失败或未加载延迟 H5 停止录音和音频合并。

H5 专项回归要求：

1. 功能开关关闭时，H5 行为与当前生产版本一致。
2. Community-1 正在处理 PC 录音时，H5 实时字幕仍能正常推送到 PC。
3. H5 录音分片数量、ACK、重试和合并文件时长没有变化。
4. Community-1 主动失败时，H5 仍能停止录音并完成上传。
5. H5 未上传完成时，PC 端仍不能结束会议。
6. PC 与 H5 同时录音时，H5 登录身份优先，不能被匿名发言人覆盖。
7. 关闭 Community-1 后无需修改或迁移任何 H5 数据。
