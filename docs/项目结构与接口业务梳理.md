## 1. 项目定位

本项目是面向国企、事业单位、政府相关业务人员的 AI 合规审查 Demo，核心目标不是做通用聊天工具，而是把“材料提交、规则匹配、AI 审查、问题定位、整改导出、归档留痕”做成可操作的业务工作台。

当前业务主线分为 7 类：

| 业务类型 | 面向用户 | 主要价值 | 前端入口 |
| --- | --- | --- | --- |
| 合规驾驶舱 | 领导、合规负责人、审计人员 | 快速查看风险态势、待处理事项、核心指标 | `StatisticalDashboard.jsx` |
| 三重一大审查 | 业务经办、合规专员 | 上传材料或粘贴文本后按事项类型生成审查意见 | `ComplianceAudit.jsx`、`ComplianceAuditFocus.jsx` |
| OA 审批联动 | 流程管理人员 | 模拟事项流转、节点拦截、审批凭证联动 | `OAWorkflow.jsx` |
| 归档中心 | 审计、合规、档案人员 | 查询历史审查记录、保留证据链 | `DecisionArchive.jsx` |
| 合规问答 | 业务人员、法务人员 | 基于知识库检索制度、案例、口径 | `KnowledgeBase.jsx` |
| 合同审查 | 法务、采购、业务部门 | 合同预览、风险高亮、条款跳转、采纳建议、导出审查版 | `CaseAnalysis.jsx`、`OfficeEditor.jsx` |
| 后台管理 | 管理员 | 维护知识文件、规则 PDF、用户账号 | `KnowledgeLibrary.jsx`、`RulesLibrary.jsx`、`UserManagement.jsx` |

## 2. 技术栈与运行方式

### 2.1 前端

- 框架：React 18
- UI 组件：Ant Design、Ant Design Icons、Ant Design X
- 构建工具：Vite
- 文档预览：`docx-preview`
- 主要目录：`frontend/src`
- 开发服务端口：`3001`

常用命令：

```bash
cd "/Users/macos/Documents/ai 合规 demo 4:28/frontend"
npm run dev
./node_modules/.bin/vite build
```

说明：当前环境中 `npm run build` 可能因脚本无法解析 `vite` 失败，直接执行 `./node_modules/.bin/vite build` 可完成构建。

### 2.2 后端

- 框架：FastAPI
- 主服务文件：`backend_full.py`
- 默认端口：`8000`
- 主要能力：SSE 流式审查、文件上传解析、知识库管理、合同审查、用户鉴权、规则管理

常用命令：

```bash
cd "/Users/macos/Documents/ai 合规 demo 4:28"
/Users/macos/miniconda3/bin/python backend_full.py
```

### 2.3 OnlyOffice 状态

项目里仍保留 OnlyOffice 相关历史代码和 Docker 目录，例如：

- `DocumentServer/`
- `onlyoffice_data/`
- `backend_full.py` 中的 `/doc/edit_url`、`/doc/editor_page/{saved_name}`、`/doc/plugin/audit_navigator/*`、`/doc/callback`

但当前合同审查页面的主要使用路径已经不是 OnlyOffice 编辑器，而是：

1. 前端通过 `/api/doc/upload` 上传合同；
2. 前端用 `docx-preview` 做 Office 兼容预览；
3. 后端通过 `/contract/map_doc_structure`、`/contract/analyze` 输出条款结构和风险点；
4. 前端在本地预览中完成高亮、跳转、问题卡片联动；
5. 通过 `/doc/submit_suggestion`、`/doc/export_reviewed` 生成审查版文档。

后续 UI 升级时应把 OnlyOffice 作为历史兼容能力处理，不应再把它作为合同审查主叙事。

## 6. 数据存储与副作用

| 路径 | 数据类型 | 产生来源 | 风险点 |
| --- | --- | --- | --- |
| `data/audit_history.json` | 审查历史 | `/audit_stream`、归档相关逻辑 | UI 改造不能改变字段含义，否则归档页会断 |
| `data/auth/users.json` | 用户账号、角色、部门 | 用户管理接口 | 不应直接手改，避免登录失败 |
| `data/custom_rules/files.json` | 自定义规则文件索引 | 规则上传/删除接口 | 文件记录与真实文件需保持一致 |
| `data/docs/` | 上传文档、生成文档、元数据 | `/doc/upload`、导出接口 | 上传文件多，不能批量清理 |
| `data/contracts/*.issues.json` | 合同风险点缓存 | 合同审查接口 | 前端问题卡片、高亮、导出依赖此数据 |
| `chroma_db/` | 向量库索引 | `/ingest_file`、向量化接口 | 删除会导致知识库问答失效 |
| `rules/` | 规则图片和制度展示资源 | 演示资源/规则图库 | 首页和规则图册可能依赖 |
| `logs/` | 服务日志 | 运行过程 | 可用于排查问题 |
| `onlyoffice_data/` | OnlyOffice 历史运行数据 | OnlyOffice 服务 | 当前非合同主路径，不建议纳入新 UI 主流程 |

## 7. 主要业务流程

### 7.1 登录与权限

1. 用户在 `LoginPage.jsx` 输入账号密码。
2. 前端请求 `POST /api/auth/login`。
3. 登录成功后将 token 写入 `localStorage`。
4. `App.jsx` 启动时请求 `GET /api/auth/me` 恢复当前用户。
5. 如果用户角色为 `admin`，侧边栏显示 `规则 PDF` 和 `用户管理`。

UI 升级注意点：登录页要明确“账号、密码、登录失败原因”，不要引入复杂营销式视觉；政府用户更需要稳定、可信、低干扰。

### 7.2 合规驾驶舱

1. 用户进入首页。
2. 页面聚合展示今日处置结论、重大事项风险、当前事项路径、风险雷达、异常快照、年度 KPI。
3. 用户根据首页提示进入三重一大、合同审查、归档中心等具体处理页。

UI 升级注意点：首页不应堆所有信息，而应回答三个问题：

- 现在有什么风险？
- 我下一步要处理什么？
- 处理入口在哪里？

### 7.3 三重一大审查

1. 用户选择事项类型。
2. 用户粘贴材料文本，或上传文件后走 `/parse_file` 提取文本。
3. 可选择自定义规则文件作为补充审查依据。
4. 前端请求 `/api/audit_stream`，后端以 SSE 形式返回审查过程和结果。
5. 页面展示 AI 审查结果、风险判断、建议整改内容。
6. 审查结果进入历史归档。

UI 升级注意点：保留完整模式和极简模式，但默认入口应偏向极简。完整模式给熟练人员和演示人员使用。

### 7.4 合同审查

1. 用户上传合同。
2. 后端保存到 `data/docs/`。
3. 前端调用 `/api/contract/map_doc_structure` 建立合同结构。
4. 前端用 `docx-preview` 进行 Office 兼容预览。
5. 用户点击 AI 审查，前端调用 `/api/contract/analyze`。
6. 后端生成问题列表，写入 `data/contracts/*.issues.json`。
7. 前端在右侧展示审查结果，左侧合同同步高亮。
8. 用户可定位条款、采纳建议、自定义修改。
9. 用户通过 `/api/doc/export_reviewed` 下载审查版文档。

UI 升级注意点：这是典型“左文档、右问题、底部导出”的工作流，应强化步骤感，弱化技术概念。按钮文案优先使用“定位条款”“采纳建议”“下载审查版”，少用“结构映射”“重新分析”等技术词。

### 7.5 知识库问答

1. 用户在合规问答页输入问题。
2. 前端请求 `/api/kb_stream`。
3. 后端基于向量库召回制度、案例或文档片段。
4. 页面流式展示回答。

UI 升级注意点：应让用户知道答案来自知识库，不是泛泛聊天。建议展示“引用来源、匹配文件、更新时间”。

### 7.6 知识文库管理

1. 管理员上传或登记知识文件。
2. 文件可通过 `/parse_file` 提取文本。
3. 通过 `/ingest_file` 或 `/api/knowledge_files/{file_id}/vectorize` 写入向量库。
4. 知识文件状态影响合规问答可用性。

UI 升级注意点：管理界面要突出状态字段，例如“未上传、已上传、已解析、已向量化、已绑定”，不要只显示技术按钮。

### 7.7 规则 PDF 管理

1. 管理员上传制度或规则 PDF。
2. 后端记录在 `data/custom_rules/files.json`。
3. 三重一大审查页面可选择这些规则作为补充依据。

UI 升级注意点：这里是后台维护页，不应做成大屏风格，应以表格、筛选、状态、更新时间为主。

### 7.8 归档中心

1. 后端保存审查历史。
2. 前端通过 `/api/audit_history` 读取。
3. 用户查看事项、风险等级、时间线和审查结论。

UI 升级注意点：归档中心的重点是“查得快、看得懂、能追溯”。需要保留筛选、时间、事项类型、风险等级等字段。

## 8. 当前问题与 UI 升级边界

### 8.1 当前体验问题

| 问题 | 表现 | 后果 |
| --- | --- | --- |
| 首页信息混杂 | 业务指标、流程、风险、入口堆在同一层级 | 新用户不知道先看哪里、点哪里 |
| 多个审查入口认知负担高 | “三重一大”和“三重一大极简版”并列 | 政府业务人员需要培训后才知道该用哪个 |
| 技术词偏多 | “向量化”“结构映射”“SSE”“OnlyOffice”等概念容易露出 | 用户以为要理解技术才能操作 |
| 合同审查链路长 | 上传、预览、AI 审查、定位、采纳、导出步骤较多 | 如果没有步骤引导，用户容易漏操作 |
| 后台管理页和业务办理页气质混合 | 工作台、大屏、表格管理混在一起 | 产品主次不清 |
| 1080p 高度压力 | 首页和复杂页面容易超出首屏 | 演示截图需要缩放，现场体验不稳定 |

### 8.2 不影响功能的 UI 升级边界

后续升级应遵守以下边界：

| 可改 | 不应改 |
| --- | --- |
| 视觉层级、布局、颜色、间距、按钮顺序 | API 路径、请求体字段、响应字段 |
| 页面文案、步骤提示、空状态、错误提示 | `data/` 下已有数据结构 |
| 页面内分区和默认展开状态 | 登录 token 存储方式，除非单独设计权限升级 |
| 共享样式变量、Ant Design 主题 token | 后端文件读写路径 |
| 前端组件拆分和复用 | 合同审查的高亮、跳转、导出主流程 |
| 1080p 适配、滚动区域优化 | 知识库向量化和审查历史持久化逻辑 |

## 9. 面向国内政府人员的 UI 原则

### 9.1 信息表达

- 入口名称使用业务语言：如“合同审查”“三重一大审查”“归档中心”。
- 技术能力隐藏到说明中：如“系统正在生成审查意见”，不写“SSE 流式响应中”。
- 每个页面保留一个明确主按钮：如“开始审查”“上传合同”“下载审查版”。
- 每个复杂流程必须显示“当前步骤”和“下一步”。
- 错误提示要给处理办法：如“后端服务不可达，请检查 8000 端口服务是否启动”。

### 9.2 视觉风格

- 采用政务系统熟悉的稳定结构：左侧导航、顶部状态、主工作区。
- 首页可以更有视觉冲击，但不做营销落地页，不使用大面积装饰图。
- 主色建议使用稳重蓝绿体系，风险色使用红、橙、黄，但严格限制面积。
- 字号层级控制在 3 到 4 档，避免大标题、卡片标题、按钮文字互相抢。
- 卡片用于具体事项，不把整个页面一层层包成卡片。
- 1920x1080 下首屏要完整显示关键决策区；内部列表可以独立滚动。

### 9.3 交互规则

- 所有主流程都按“上传/输入 - 审查 - 查看问题 - 处理 - 导出/归档”呈现。
- 复杂页面优先使用左右分栏：左侧材料，右侧结论或操作。
- 对后台管理页，优先使用表格、筛选、状态标签、批量操作。
- 对审查结果页，优先使用风险等级、问题数量、定位按钮、处理状态。
- 不把帮助说明做成大段文字，应转为步骤条、状态条、空状态提示。

## 10. UI 升级分期方案

> 这是重大改动的执行计划。建议确认后再动代码。

### 阶段 A：建立统一设计底座

目标：不改业务逻辑，只统一整体视觉语言。

- 在 `App.jsx` 和 `index.css` 中建立统一主题 token。
- 统一页面背景、侧边栏、顶部栏、内容容器、卡片、状态标签。
- 统一按钮层级：主操作、次操作、危险操作、文本操作。
- 保留现有路由、接口、状态变量。

验收标准：

- 登录、首页、合同审查、三重一大、知识库、后台页视觉风格一致。
- 1920x1080 下首页关键区不溢出。
- 暗色模式如果保留，不能破坏文字可读性。

### 阶段 B：首页重构为“合规处置工作台”

目标：首页一眼看懂“这是什么、风险在哪、下一步做什么”。

- 首屏固定三块：今日结论、待办风险、快速入口。
- 弱化装饰指标，强化事项路径。
- 将 KPI 移到底部或次级区域。
- 首屏高度按 1080p 设计，不依赖浏览器缩放。

验收标准：

- 首屏不滚动即可看到系统名称、今日风险、下一步入口。
- 用户 5 秒内能判断系统用于合规审查，不是通用 BI 大屏。

### 阶段 C：三重一大审查降复杂度

目标：让普通经办人员按步骤完成审查。

- 默认展示极简审查路径。
- 完整模式作为“高级设置”或“专家模式”。
- 强化事项类型、材料输入、规则选择、开始审查的顺序。
- 审查结果分为“结论、风险、依据、整改建议”。

验收标准：

- 不看说明也能完成一次材料审查。
- 规则选择、模板生成、文件解析不互相干扰。

### 阶段 D：合同审查工作台优化

目标：强化“左预览、右问题、点击定位、处理导出”的业务闭环。

- 顶部显示合同名、审查状态、风险数量、导出按钮。
- 左侧固定文档预览，右侧固定问题列表。
- 问题卡按风险等级和处理状态分组。
- 操作按钮固定为：定位条款、采纳建议、自定义修改。
- 导出入口始终可见，但未审查时置灰并说明原因。

验收标准：

- 高亮、跳转、采纳、导出不回退。
- 用户知道审查结果在哪里，知道最后下载哪里点。

### 阶段 E：知识库和后台管理统一成“维护台”

目标：让管理人员清楚每个文件处于什么状态。

- 知识文库按状态分组：未解析、待向量化、已生效、异常。
- 规则 PDF 管理强化上传时间、来源、适用事项。
- 用户管理保留表格效率，不做大屏化。

验收标准：

- 管理员无需理解向量库原理，也能完成文件生效。
- 删除、覆盖、重新向量化等高风险操作有明确提示。

### 阶段 F：全链路 QA

目标：确认 UI 升级不破坏现有功能。

验证清单：

- 登录、退出、刷新恢复登录态。
- 首页 1920x1080 无页面级高度溢出。
- 三重一大审查能流式返回结果。
- 合同上传后能预览、审查、高亮、跳转、提交建议、下载审查版。
- 知识库问答能流式返回。
- 知识文件能上传、解析、向量化、绑定。
- 规则 PDF 能上传和删除。
- 用户管理能增删改查。
- 后端 API 路径和请求体保持兼容。

## 11. 建议优先级

如果只做一轮 UI 升级，建议顺序如下：

1. 首页：先解决“看不懂主次”和“1080p 显示不全”。
2. 合同审查：这是最有业务闭环的页面，要保证一眼知道“预览、问题、定位、下载”。
3. 三重一大极简页：让普通业务人员不用培训即可完成审查。
4. App 外壳：统一菜单、顶部状态、登录态、角色提示。
5. 知识库和后台页：最后做一致性和状态表达。

## 12. 后续开发注意事项

- 不要再以 OnlyOffice 作为合同审查主路径来设计页面；当前主路径是 Office 兼容预览加本地高亮定位。
- 不要修改 `data/`、`chroma_db/` 的结构，除非单独做迁移方案。
- 不要调整接口字段名，除非同步修改所有前端调用并补迁移。
- 不要把首页做成纯大屏展示页，它应当是业务处置入口。
- 不要让“完整模式”和“极简模式”在导航里长期并列竞争，后续应收敛为默认模式加高级设置。
- 不要用大段帮助文字替代流程设计，政府业务用户更需要稳定的步骤、明确的按钮和可追溯结果。
