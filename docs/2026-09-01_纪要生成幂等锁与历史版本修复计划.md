# 2026-09-01 纪要生成幂等锁与历史版本修复计划

## 问题

同一会议的“重新生成纪要”接口允许并发执行。用户重复点击、刷新页面或多个页面同时发起请求时，会重复执行完整 MAP/REDUCE 链路，造成：

- 同一份 101 分钟终审文本被重复拆分并调用本地 LLM；
- 8088 队列拥堵，单轮生成时间被放大；
- 后完成的旧任务覆盖先完成的新结果；
- 正常结果可能被后续降级结果覆盖；
- 页面只能显示长时间加载，无法判断任务是否仍在运行。

## 修复方案

### 1. 同会议单任务锁

- 8002 内按 `meetingId` 保存唯一生成任务。
- 同一会议已有运行任务时，后续请求复用同一个任务结果，不再创建新的 MAP/REDUCE 调用。
- 不同会议仍可按现有并发限制并行处理。
- 请求断开不取消共享生成任务，避免刷新页面导致后台任务被中断。

### 2. 生成状态

- 增加纪要生成状态查询接口。
- 状态至少包含：`idle/running/done/failed`、任务编号、开始时间、完成时间、错误信息和是否已有成果。
- 前端在任务运行时禁用重复生成按钮，并明确显示“正在生成，重复操作不会创建新任务”。
- 页面刷新后可恢复任务运行状态。

### 3. 历史生成记录

- 复用现有 `meeting_record_versions`，不修改数据库 Schema。
- 每次成功生成后保存完整成果快照、生成来源、流水线状态和生成时间。
- 历史版本接口继续提供版本详情，避免生成结果只能保留最后一份。
- 人工编辑、人工确认和 AI 生成使用不同版本说明，便于审计。

### 4. 覆盖保护

- 只有当前会议登记的活动任务可以写入最新成果。
- 已失效或被替代的任务不得覆盖当前成果。
- 生成失败保留原有成果，不写入空结果或降级半成品。

## 验收条件

1. 同一会议并发发起 5 次生成，只执行一轮 MAP/REDUCE。
2. 5 个请求得到同一份结果和同一任务编号。
3. 刷新页面后仍显示运行状态。
4. 生成完成后新增一条 AI 生成历史版本。
5. 生成失败时旧成果保持不变，状态返回失败原因。
6. 不同会议可以正常并行生成。
7. 后端定向测试和前端生产构建通过。

## 非目标

- 不修改数据库 Schema。
- 不调整 8088 模型、GPU0、8091 或 8092。
- 不改变 MAP/REDUCE 的提炼内容和证据恢复规则。
