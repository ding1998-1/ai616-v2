## 二、差距清单

### 🔴 P0 — 不修复无法交付

---

#### P0-1 · API 密钥硬编码泄露

**文件**：`.env`、`docker-compose.yml`

**问题**：
- `.env` 包含真实的 `DEEPSEEK_API_KEY`、`DASHSCOPE_API_KEY`
- `docker-compose.yml` 第 11 行硬编码了 DeepSeek API Key
- 这些文件如果和代码一起打包发给客户，密钥就泄露了

**影响**：安全事件。API 额度被盗用、数据泄露。

**修复方向**：
1. `.env` 所有密钥用 `change-me-please` 占位
2. `docker-compose.yml` 改为读取 `.env` 文件：`env_file: .env`
3. 提供 `scripts/generate-secrets.sh` 随机生成 `APP_AUTH_SECRET`、`ONLYOFFICE_JWT_SECRET`

---

#### P0-2 · Docker Compose 配置不完整，容器无法启动

**文件**：`docker-compose.yml`、`Dockerfile`、`frontend/Dockerfile`

**具体问题**：

| 问题 | 详情 |
|------|------|
| 后端端口不一致 | `Dockerfile` EXPOSE 8000，实际应用监听 8002（uvicorn 启动命令没有指定 `--port 8002`） |
| 环境变量缺失 | `docker-compose.yml` 缺少 `LLM_API_BASE`、`APP_AUTH_SECRET`、`EMBEDDING_MODEL`、`PERSIST_DIR` 等必要变量 |
| 后端依赖 ChromaDB 模型 | 容器首次启动时 `sentence-transformers` 会从 HuggingFace 下载 400MB+ 模型，无网络环境直接超时失败 |
| `.dockerignore` 不完整 | 会把 `node_modules/`、`chroma_db/`、`data/` 全部 COPY 进镜像，镜像体积可能超过 5GB |
| 前端 nginx 配置与裸机不一致 | `frontend/nginx.conf`（Docker 用）缺少 `/api/kb_stream`、`/api/meeting/` WebSocket、`/parse_file`、`/ingest_file` 等路由 |

**影响**：客户执行 `docker compose up` 后服务无法启动。

**修复方向**：
1. 统一端口为 8002，或添加 `--port` 参数
2. 补全 `docker-compose.yml` 的 `environment` 段
3. 构建镜像时预下载 embedding 模型到 `/root/.cache/huggingface/`
4. 完善 `.dockerignore`
5. 合并两套 nginx 配置为单一模板

---

#### P0-3 · APP_AUTH_SECRET 写死，多部署共享同一密钥

**文件**：`.env` 第 31 行

**问题**：JWT 签名密钥 `ai-compliance-auth-secret-key-32bytes!` 是硬编码的。如果多个客户部署同一套代码，所有客户的 JWT Token 可用同一密钥验证——一个客户的管理员 Token 可以跨客户使用。

**影响**：安全隔离失效。客户 A 的管理员可登录客户 B 的系统。

**修复方向**：部署时由脚本随机生成：`openssl rand -hex 32`

---

### 🟡 P1 — 客户部署会卡住

---

#### P1-1 · 无部署文档

**现状**：没有一份文档告诉客户"拿到代码后怎么做"。

**缺失内容**：
- 环境要求（Python 3.10+、Node 18+、Nginx、系统依赖）
- 最少配置项说明（哪些必填、哪些可选）
- Docker 部署步骤
- 裸机部署步骤
- 首次启动后如何创建管理员账号
- 如何接入自己的 LLM API
- 常见故障排查

**修复方向**：编写 `docs/部署手册.md`、`docs/配置说明.md`

---

#### P1-2 · Embedding 模型需运行时下载

**依赖**：`sentence-transformers` → `shibing624/text2vec-base-chinese`（约 400MB）

**问题**：
- 首次启动时自动从 HuggingFace 下载，国内网络通常很慢或不可达
- Docker 容器重建后模型缓存丢失（除非单独挂载 volume）
- Bare-metal 部署时，客户需要配 HuggingFace 镜像（`HF_ENDPOINT=https://hf-mirror.com`）

**当前处理**：
- systemd service 已配 `HF_ENDPOINT=https://hf-mirror.com`
- Docker 环境未配置

**修复方向**：
1. 将模型目录挂载为 Docker volume
2. 或者构建镜像时预下载模型到镜像内
3. 文档说明离线环境下的模型准备方法

---

#### P1-3 · OnlyOffice 是硬依赖但未说明

**现状**：`docker-compose.yml` 包含 onlyoffice 服务，裸机部署完全没有提及。

**问题**：
- 合同在线编辑、DOCX 预览等功能依赖 OnlyOffice
- 客户如果不需要文档编辑，OnlyOffice 应该可选
- OnlyOffice Document Server 需要至少 4GB 内存，对小服务器是负担

**修复方向**：
1. 将 OnlyOffice 设为可选组件
2. 文档说明哪些功能依赖 OnlyOffice
3. 提供 `docker-compose.onlyoffice.yml` 作为可选叠加文件

---

#### P1-4 · 数据库无迁移机制

**现状**：SQLite 表结构在 `_init_app_db()` 中用 `CREATE TABLE IF NOT EXISTS` 创建。

**问题**：
- 新版本加了字段怎么办？没有 ALTER TABLE 逻辑
- 升级时数据丢失风险
- 无法回滚到旧版本

**修复方向**：
1. 引入简单的 migration 机制（如 `backend/migrations/` 目录 + 版本号）
2. 或至少提供数据导出/导入脚本

---

#### P1-5 · 前端需预构建，增加部署复杂度

**现状**：裸机部署需要 Node 18+ 环境运行 `npm run build`。

**问题**：
- 客户服务器通常没有 Node 环境
- 增加了部署步骤和出错概率
- Docker 环境下已在 `frontend/Dockerfile` 中多阶段构建，没问题

**修复方向**：
1. 裸机部署文档中明确 Node 要求
2. 或提供预构建的 `dist/` 作为 release artifact

---

#### P1-6 · 数据持久化路径不明确

**问题**：
- Docker volume 挂载哪些目录？目前 compose 挂了 `chroma_db`、`data`、`.env`，但 `data/docs` 内的合同文件、`data/uploads` 的上传文件、`data/meeting_files` 的会议文件都在 `data` 下——这部分 OK
- ChromaDB 数据在 `chroma_db/` 下，也已挂载
- 但 embedding 模型缓存（`~/.cache/huggingface/`）未挂载，容器重建后需重新下载

**修复方向**：
1. 文档中明确列出所有需要持久化的路径
2. Docker 环境增加 `~/.cache/huggingface/` 的 volume

---

#### P1-7 · 配置项分散，无单一权威来源

**现状**：配置散落在三个地方：
- `.env`：LLM Key、ChromaDB 路径、OnlyOffice JWT
- `docker-compose.yml`：`DEEPSEEK_API_KEY`（硬编码）、`ONLYOFFICE_JWT_SECRET`
- `backend/config.py`：默认值、路径推导

**问题**：同一个配置项在多处定义，修改时容易遗漏，出问题时不知道哪个生效。

**修复方向**：
1. `.env` 作为唯一配置入口
2. `docker-compose.yml` 通过 `env_file` 读取
3. `config.py` 只做默认值 fallback
4. 提供 `.env.template` 含所有配置项及注释

### 🟢 P2 — 生产级加固

---

#### P2-1 · 无 HTTPS / TLS

**现状**：全 HTTP 明文传输，JWT Token、密码、合同内容都在网络上裸奔。

**修复方向**：
- Nginx 层配置 Let's Encrypt 自动证书
- 或提供配合客户现有 TLS 网关的部署说明

---

#### P2-2 · 无 API 速率限制

**现状**：LLM API（DeepSeek）调用无频率控制。

**影响**：恶意或误操作可短时间内消耗大量 API 额度。

**修复方向**：FastAPI 中间件或 nginx `limit_req` 做令牌桶限流。

---

#### P2-3 · 日志管理缺失

| 问题 | 详情 |
|------|------|
| 日志文件无限增长 | `backend_server.log` 无轮转，目前可能已很大 |
| 日志级别统一 | `logging.basicConfig(level=INFO)`，不能按模块调整 |
| 无结构化日志 | 纯文本 `logger.info(f"...")` 不易检索分析 |
| 审计日志与业务日志混在一起 | 同一文件输出 |

**修复方向**：
1. systemd journal 接管日志（当前已配 `StandardOutput=append:...log`）
2. 或引入 `loguru` 做轮转（已在 `requirements.txt` 中但未使用）
3. 审计日志单独输出

---

#### P2-4 · Docker 镜像未优化

| 问题 | 详情 |
|------|------|
| 后端基础镜像过大 | `python:3.10` 完整镜像约 1GB，可用 `python:3.10-slim`（~200MB） |
| 无 healthcheck | Docker 不知道容器是否健康，无法自动重启 |
| `.dockerignore` 过于简陋 | 只有 `node_modules`，会复制大量无关文件 |
| 无镜像标签策略 | 每次构建都是 `latest`，无法回滚 |

**修复方向**：
1. 改用 `python:3.10-slim` + 多阶段构建
2. 添加 `HEALTHCHECK --interval=30s CMD curl -f http://localhost:8002/health`
3. 完善 `.dockerignore`
4. 构建脚本加时间戳标签

---

#### P2-5 · 无监控/告警

**现状**：没有任何指标暴露（Prometheus metrics、健康端点只有 binary ok/fail）。

**修复方向**：至少加上 Docker healthcheck + 关键指标的 `/metrics` 端点。

---

#### P2-6 · 备份策略不完整

| 问题 | 详情 |
|------|------|
| 备份脚本存在 | `backup_db.py` 只备份 `app.db` |
| JSON 文件无备份 | `users.json`、`files.json`、`legal_cases.json` 等未纳入 |
| ChromaDB 无备份 | 43MB 的向量数据未纳入 |
| 文档文件无备份 | `data/docs/` 下的合同文件未纳入 |
| 无自动清理 | 旧备份无限累积 |

**修复方向**：扩展 `backup_db.py` 覆盖所有数据，加保留策略。

## 五、为什么现在就可以开始部署（附注意事项）

尽管有上述差距，**当前系统已经可以在受控环境下部署**：

```bash
# 当前可行的裸机部署步骤（Ubuntu 22.04）
git clone <repo>
cd ai616

# 1. 安装依赖
pip install -r requirements.txt
sudo apt install nginx

# 2. 修改配置
cp .env.example .env
nano .env   # 填入 LLM API Key

# 3. 构建前端
cd frontend && npm install && npm run build && cd ..

# 4. 部署 nginx
sudo cp nginx-fixed.conf /etc/nginx/sites-available/ai-compliance
sudo ln -s /etc/nginx/sites-available/ai-compliance /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 5. 启动后端
sudo cp ai-compliance.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ai-compliance

# 6. 验证
curl http://localhost:8002/health
```

**注意事项**（当前必须手动处理）：
1. 修改 `.env` 中的 API Key 为你自己的
2. 首次启动需等待 embedding 模型下载（约 2-5 分钟）
3. 默认管理员账号需要手动在 `data/auth/users.json` 中创建
4. ChromaDB 数据目录需要有写权限
